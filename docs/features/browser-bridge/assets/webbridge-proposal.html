Proposal · Browser extension · 2026-11-18

Evo Webbridge

Evo in the person's own Chrome or Edge: a side panel to chat next to the page, and an agent that opens and works in tabs of its own, in the signed-in profile, with the same browser tools as the built-in browser.

Status · Draft spec.md plan.md ADR 0012

What changes for the person

  • An Evo side panel in Chrome and Edge, on any page.
  • The agent opens background tabs in a tab group named after the chat.
  • Drag a tab into the group to hand it over, out to take it back.
  • Per-site permission: Ask, Allow or Block.
  • Stop and Take over on the page, in the panel and in the app.

What is new in the code

  • An MV3 extension, no host permissions.
  • evo-bridge-host, started by the browser.
  • webbridge/ in the shell: pipe, groups, sites, panel.
  • A TabHost seam under the page driver.

What stays the same

  • The engine and its protocol.
  • The 29 browser_* tools.
  • Approval modes; sites only add rules.
  • No network port.

01 · What the person sees

The browser while an agent works

The person asks in the side panel; the agent opens the billing site in a background tab of the chat's group, works in it, and asks once before acting on a site set to Ask. Every sign of agent work comes from three places: the tab group, Evo's in-page indicator and the browser's own debugging notice, which Evo cannot hide.

02 · How it fits together

Processes and channels

The extension is a thin client: it relays DevTools commands for tabs in Evo's groups and hosts the side panel. The browser starts evo-bridge-host, which joins the shell over a named pipe. Every decision stays in the shell (webbridge): which chat owns a tab, what the gate allows, which engine runs. The browser tools reach the tab through BridgeHost, a second implementation of the page driver's tab host beside today's WebView2 one.

03 · How a call travels

The agent opens a page and clicks

The browser tools don't know which browser serves the page. A Webbridge tab id (chrome:work:1234) routes the call through BridgeHost; the host process only frames bytes and is left out of this picture.

04 · Who owns a tab

A tab's life in Webbridge

Ownership is the tab group: a tab belongs to a chat while it sits in that chat's group, and only that chat's agent can name it. The debugger is held only while the agent is using the tab.

05 · What the agent may do

The gate on a Webbridge tab

Site permissions sit inside the existing approval gate; they add rules, never remove one. Reads (page text, screenshots, the accessibility tree) never ask, but stop at a Block site like everything else.

06 · Who can reach it

Trust boundaries

Web pages, other extensions, other users and the network must not reach the bridge. Code already running as the same user is out of scope: it could read the browser profile anyway. Three checks stand in the way, and none of them is a secret the extension keeps.

07 · The wire

Messages between the extension and the shell

JSON, one message per native-messaging frame (4-byte length, then UTF-8). The same frames cross the pipe. Large app → extension messages are split into chunk frames, because the browser accepts at most 1 MB per frame from a host.

MessageDirectionPurpose
hello / welcomeext → app / app → extBrowser, profile id and label, version, whether policy allows the debugging API; protocol version.
open, adopt, releaseapp → extOpen a tab in a chat's group; take a tab the person picked or handed over; let a tab go.
attach, detach, cdpapp → extHold or release the debugger; one DevTools command (with a child-frame session when needed).
result, eventext → appAnswer to a request (gone, refused, restricted, busy on failure); DevTools events.
tab, groupext → appA tab joined, left, closed or changed; a group closed.
overlay, controlbothIndicator state; Stop, Take over, Hand back, Stop all from the page or the popup.
panelbothSide panel ops: chats, open, new, send, stop, answer, models, set_model, set_effort, set_mode, attach, open_in_app; back: chat, event, question.

Tools the agent sees

  • target on every browser_* tool: builtin (default), chrome, edge, or chrome:<profile>.
  • Tab ids such as chrome:work:1234; a tab id alone picks the browser.
  • browser_tabs {action: "choose"} asks the person to pick one of their open tabs; the agent sees titles and sites only.
  • Not on Webbridge tabs: the download folder and downloads list.

What Evo keeps

  • ~/.evo/agent/webbridge/sites.json: Allow and Block per site; everything else is Ask.
  • profiles.json: known browser profiles and their labels.
  • In memory only: groups, tab owners, leases, takeover state, panel sessions.
  • Settings: webbridge.enabled, newChatWorkspace, leaseSeconds, voiceInput.

08 · Getting there

Proposed phases

The order the tasks will follow once the spec and plan pass their gates. Each phase ends with something a person can try.

Phase 0 · Spike

Prove the risky parts

Screenshots of background tabs in Chrome and Edge; the debugging API under company policy; a minimal extension to host to pipe.

Phase 1

Connect

Host, pipe, peer checks, host registration from Settings, connection state.

Phase 2

Drive a tab

TabHost refactor and BridgeHost; tab groups; all 29 tools on a Webbridge tab.

Phase 3

Stay in control

Site permissions in the gate, in-page indicator, Take over, Stop all.

Phase 4

Side panel

Chat, history, questions; model, effort and mode; attachments; voice input.

Phase 5

Ship

Chrome Web Store and Edge Add-ons listings; macOS and Linux registration.

09 · Still open

Questions before the spec is accepted

  • How long is a tab held? Proposed: from the first call while the turn runs, released 60 s after it ends.
  • Where do agent tabs open? Proposed: background tabs in the last focused window; a window of their own only if background screenshots fail.
  • Which chats does the panel offer? Proposed: recent chats of every workspace; new ones in the workspace set in Settings.
  • One site list or one per profile? Proposed: one list for all browsers and profiles.
  • Publish to the stores in this feature? Proposed: yes, as the last phase; unpacked with a fixed id until then.
  • Act while the person types in the tab? Proposed: no; wait until they stop for 5 s.
  • Which speech-to-text? Proposed: the browser's own, off by default, with a notice that audio goes to the browser maker's service.
  • Known risks: policy can turn the debugging API off; a page can hide Evo's indicator (the browser's notice and the group stay); MV3 workers restart on update.
